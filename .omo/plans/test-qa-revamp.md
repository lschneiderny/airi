# test-qa-revamp - Work Plan

## TL;DR (For humans)

**Who this is for and what changes for them:** Luke and the agent lanes that run checks before landing work. After this plan, an everyday check re-tests only what changed since the last good check, live app testing no longer freezes every other lane, and one guide says exactly which checks a change needs.

**What you'll get:** A faster everyday check plus a full branch check before landing, a CPU queue that lets app testing and unit tests run side by side, fills idle cores instead of waiting in strict order, shares slots fairly when several lanes wait, and watches real CPU pressure, recorded wait and failure history with summary commands, fewer and cheaper browser test runs, one shared app-session core under the QA commands, cleaned-up flaky tests, and one testing guide that the agent instructions point to.

**Why this approach:** Measured history shows the test step of the everyday check costs about ten hours over five days, mostly because it re-tests the whole branch on every run and queues for CPU once per command. Fixing scope and queueing removes most of that cost. Moving live testing off the whole-machine lock keeps lanes moving. The guide makes live testing required only for visible motion changes, plus one clean-start check before landing.

**What it will NOT do:** It will not remove any QA command, merge every test configuration into one, loosen what the result cache treats as a pass, or run live app testing on Luke's own desktop.

**Effort:** XL
**Risk:** Medium - the everyday check becomes incremental, so the branch check before landing must stay mandatory.
**Decisions to sanity-check:** the new 4-6 slot "live" CPU class; the 60-second limit after which a waiting large request stops others from jumping ahead (whole-machine timing runs are exempt and simply wait for a quiet moment); the CPU-pressure thresholds for holding or overcommitting grants; frame-timing runs still take the whole machine; the guide lives at `docs/ai/testing.md`; heavy plan lanes are capped at three.

## Scope
### Affected user and ideal state
**Affected user:** (1) Luke, who waits on plan lanes and lands their work; (2) worker agents that run `pnpm verify`, `pnpm test:run`, and `qa:*` commands and read `AGENTS.md`, skills, and READMEs to decide what to run; (3) programs that consume the results: the cpu-slots broker, the verify pass cache, and qa-tools evidence runs. Today every verify on a plan branch re-tests the whole branch, queues for CPU up to 20 times, and any live QA run blocks every worktree. After this plan, the commit loop checks only new changes, a gate checks the branch once, live QA shares the CPU budget, and one guide states the required checks.
