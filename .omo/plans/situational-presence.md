# situational-presence - Work Plan

## TL;DR (For humans)
<!-- Fill this LAST, after the detailed plan below is written, so it summarizes the REAL plan. -->
<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**Who this is for and what changes for them:** You, at your desk with the character in a corner of the screen. She will know what you are doing and for how long, speak up on her own now and then when something real changes, stay quiet while you talk, game in fullscreen, sit in a call, or ask her not to disturb you, and back off when you ignore her.

**What you'll get:** A short "what's going on" summary on every reply instead of a raw dump; a Windows sensor for the app and window in front; occasional unprompted remarks that she can choose to skip; plugin notifications that become normal, paced chat turns; a sturdier cue format so weaker local models still animate her, including where she looks; your persona fully owned by your character card; a Presence settings page and a developer inspector showing what she knows and why she spoke or stayed quiet.

**Why this approach:** Code decides when a moment exists and the model only decides whether and what to say, so remarks are timely and never random; everything flows through the existing chat pipeline, so her voice, face, captions and history work the same for unprompted lines as for replies.

**What it will NOT do:** No chatter when nothing has changed, no constant screen watching, no new game integrations, no changes to the plugin protocol, nothing remembered across restarts, no Kirie or Godot changes.

**Effort:** XL

### Must have
- Four layers: sensors -> pure situation model -> pure opportunity gate -> delivery through the existing chat runtime FIFO (`createChatOrchestratorRuntime`). The gate decides when; the model decides whether/what and may reply only `<|SILENT|>`.
- The situation block is the ONLY ambient-context channel; conversation history stays verbatim and ordered; messages addressed to her bypass the gate.
- Every existing context source becomes a sensor adapter in this plan: vision context, Minecraft context, plugin `context:update`, the runtime-prompt live state (exposed expressions, expression-state/mood).
- Windows foreground sensor via koffi FFI in Electron main: `GetForegroundWindow`, `GetWindowTextLengthW`/`GetWindowTextW`, `GetWindowThreadProcessId`, `OpenProcess`+`QueryFullProcessImageNameW`+`CloseHandle`, `SHQueryUserNotificationState`. Full titles reach the model after normalization; AIRI's own processes are excluded entirely; denylisted apps are reported by app name and category only, never by title.
- Automatic `shownAt` (first render) and `addressedAt` (set when the gate fires) mention flags; no model bookkeeping marker.
- Engagement backoff; no idle chatter; SILENT declines leave only a control record.
- Spark: observe + gate (decision D13 in the draft); commands-only agent for notifies whose destinations go beyond `character`; widget reaction requests become forced unprompted turns returning the reply text; side-path speech removed.
- Muted "spoke up about X" cue in chat, ON by default with a setting to disable it.
- In-memory situation state per run; leader-owned; not a synced Pinia state.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- No idle chatter (speaking when nothing changed), no vision-on-change capture, no new game integrations.
- No `input:unprompted` (or any) change to `@proj-airi/plugin-protocol` / `server-shared` event unions; `origin` is a local runtime field.
- No desktop/window/mood/notebook concepts inside `packages/core-agent`; the runtime learns only `origin` and a decline marker.
- No second queue or scheduler inside the runtime; unprompted turns use the existing per-session FIFO.
- No `[Context]` passthrough kept "temporarily" for any source; no NOTICE-marked fallback that keeps the raw dump.
- No situation block or window title stored in `ChatHistoryItem`; trigger text uses app label/category/duration only, never the raw title.
