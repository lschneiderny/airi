# LLM prompt

This file describes the code on `main`. A change that makes a statement here false updates this file in the same commit. These rules win over the ADRs in `docs/ai/adr/`; the ADRs record the history behind them.

The system prompt of every character turn is built by one pure function, `composePrompt` in `packages/stage-shared/src/stage-contract/compose.ts`. It reads no locale, store, or clock. It sorts the supplied [segments](glossary.md#prompt-segment) by `PROMPT_SEGMENT_ORDER`, fits each segment to its entry in `PROMPT_SEGMENT_BUDGETS`, drops empty segments, and joins the rest with a blank line. The one exception to the join is that the card follows the format rules directly. The function returns the full text, the prefix, the tail, and a size report with one entry per supplied segment. An unknown or duplicate segment id throws. Overflow never throws.

Hosts render the segment texts. In the app, `useChatPrompt` in `packages/stage-ui/src/stores/chat/prompt.ts` returns `buildChatPromptSegments`, which is the only builder of character-turn segments. Every app path that makes the character speak or act calls it, including the Spark Notify commands-only agent. See [Paths](#paths).

## Rules

The [one prompt composer ADR](../adr/2026-11-20-one-prompt-composer.md) records why these rules hold. The numbers are those of the [Target](#target) list.

1. **One composer for every character call.** Every LLM call that speaks or acts as the character, including the Spark Notify commands-only agent, builds its system prompt through `composePrompt` from the segments that `buildChatPromptSegments` assembles. Paths differ only by declared `ChatPromptInput` fields, never by their own concatenation. Calls that do not speak as the character, such as thread extraction and the artistry director, keep their own task prompts and budgets outside the composer (see [Paths](#paths)).
2. **Same segments, same caps.** Every path receives the same segments under the same budgets. Plugin text with system authority is the capped `plugin` segment on every path.
3. **One memory source.** The memory index is the speaking character's: the character that owns the session the turn belongs to, through `personaOf` in `useChatSessionStore`. The Spark Notify commands-only agent reads the active session's character.
4. **No segment without a producer.** A segment id that no app path produces is deleted from `PROMPT_SEGMENT_ORDER`, `PROMPT_SEGMENT_BUDGETS`, and the qa-tools fixtures.

## Segments

The overflow policies are defined by `OverflowPolicy` in `packages/stage-shared/src/stage-contract/compose.ts`:

- `fixed`: host-written text with no budget. It is never cut or flagged.
- `warn`: the text is kept, and the report sets `overBudget`. Nothing is cut.
- `truncate`: text over the budget is cut, and `PROMPT_TRUNCATION_MARKER` is appended inside the budget.
- `drop-oldest`: list entries are dropped from the front until the entry cap and the char cap both hold. The header is not counted, and it stays when every entry is dropped.

The "enforced in code?" column states what `composePrompt` does when a segment is over its budget. Budgets are in characters, not tokens.

The `card` segment holds more than the card's own prompt. `getSystemPrompt` joins the card's system prompt, description, personality, and scenario, the artistry widget instruction of the card, and, for the active card only, the section that `formatLive2DActPrompt` (`packages/stage-ui/src/constants/prompts/live2d-act.ts`) writes for the Live2D expressions and motions that the card enables (see [Known gaps](#known-gaps)). In a [recipe](glossary.md#recipe)'s own session, `cardSupplement` adds the steps of the recipe through `composeRecipeSpacePrompt` (`packages/stage-ui/src/stores/chat/prompt-recipe.ts`). The steps stay the same for every request of that session, so its prefix stays stable. `toolGuidance` adds `composeDrawCardPrompt` (`packages/stage-ui/src/tools/draw-card.ts`) to the `toolset` segment while the session draws reply cards: the owner's own conversation, with reply cards on. `sessionPromptSegments` in `useChatStore` sets both fields, and no other caller does.

The memory header tells the model never to save what a recipe already holds.

The prefix (`format`, `card`, `register`, `contract`) changes only when the card, the [conversation register](glossary.md#conversation-register), or the locale of the contract changes. The provider's prompt cache depends on it. The tail follows the prefix, and `actions` leads the tail because the exposed clips change only when the user curates them. `composeSystemPrompt` in `packages/stage-shared/src/stage-contract/index.ts` returns the prefix of the format, card, and contract segments. With a register section joined to the card, its output is byte-identical to the composed prefix.

These parts of a request are not system-prompt segments and do not pass through the composer: the [situation block](glossary.md#situation-block) and the [character context](glossary.md#character-context), which the runtime attaches to the last user turn through the runtime context providers of `useChatStore` in `packages/stage-ui/src/stores/chat.ts`; the trigger message of an [unprompted turn](glossary.md#reach-out); per-message timestamps; the skill text of a recipe that the owner's message invoked by keyword, which is stored with that message (`ChatInvokedSkill`) and rendered into its user turn; the prefix that marks a stored [notice](glossary.md#notice) as not from the owner, and the line that lets the model stay quiet about it; and tool schemas.

The output cap is not a segment. The Consciousness store's `replyMaxTokens(provider, model)` picks it, and it is sent as `maxTokens` on every model request of chat turns, [background task](glossary.md#background-task) turns, notice turns, `ingest`, unprompted turns, and the [Spark Notify](glossary.md#spark-notify) agent. A request that does not reason gets `REPLY_MAX_TOKENS` (320) from `packages/stage-shared/src/stage-contract/index.ts`. A request that may reason gets `REASONING_REPLY_MAX_TOKENS` (2048), because providers count reasoning tokens toward the cap: one that carries reasoning `enabled`, and one to a cloud provider that AIRI sends no reasoning mode, such as Anthropic, whose Claude 5 models always reason. A local provider or a generic OpenAI-compatible endpoint without a reasoning mode keeps 320. `replyMaxTokensFor` in `packages/stage-ui/src/libs/providers/reply-max-tokens.ts` holds the rule; see the [reasoning reply cap ADR](../adr/2026-11-18-reasoning-reply-cap.md).

## Paths

**Chat turns (typed and voice).** `useChatStore` in `packages/stage-ui/src/stores/chat.ts` prepares a send and builds a resolver that runs before each model request, so a tool step that edits the card or memory reaches the next request. The resolver reads the character that owns the session, not the selected card. It calls `buildChatPromptSegments` with that character, the voice context and control events of a voice turn, and the sticker catalog from the stickers store. It then composes the prompt with `composePrompt` and sends the output cap for the character's provider and model. The provider and model come from that character's card. The runtime, `createChatOrchestratorRuntime` in `packages/core-agent/src/runtime/chat-orchestrator-runtime.ts`, sends the composed text as the system message and also writes the first request's prompt into the display projection, so hooks and diagnostics see what was sent. The stored session system message, which `useChatSessionStore` in `packages/stage-ui/src/stores/chat/session-store.ts` builds with `composeSystemPrompt` from the card, the register section, and the contract, is replaced for every request that has a resolver. Every chat path in `useChatStore` passes a resolver.

**`ingest`.** The `ingest` action of `useChatStore` sends a message with the caller's provider, model, temperature, and top-p. It captures `buildChatPromptSegments` once, when it is called, for the session's character, and adds the sticker segment from the caller's catalog or the stickers store. It never supplies `voice`, `control`, `unprompted`, or `plugin`. It sends the same output cap through the same resolver as chat turns, and it adds no memory tools of its own. The callers are devtools and stress tools, for example `useMarkdownStressStore` in `packages/stage-ui/src/stores/markdown-stress.ts`.

**Tools of a chat turn.** A typed or voice turn carries the tools that the session selected, the wake word tool, and the memory tools. `withRunTools` in `useChatStore` adds, in the owner's own conversation only, the use-recipe tool (`createUseRecipeTool`), the propose-recipe tool (`createProposeRecipeTool`) while recipe proposals are on, and the draw-card and icon search tools while the session draws reply cards. A recipe's own session gets none of them.

**Recipes.** A recipe reaches a turn in three ways, and none adds a segment or a model call of its own.

- A keyword in the owner's message invokes it (`matchKeywordRecipes` in `packages/core-agent`). The runtime stores the skill text with the message and renders it into that user turn, for this reply and later ones.
- A decision recipe adds the judge tool (`createJudgeRecipeTool` in `packages/stage-ui/src/tools/judge-recipe.ts`) to the turn. The model picks an answer, and code (`judgeDecision`) chooses what follows: a reply, silence, a hint, or another recipe.
- The use-recipe tool starts a recipe by name.

Only a message of the owner in the owner's own conversation invokes or judges a recipe. A notice, a background task, a scene session, and an unprompted turn never do.

**Background tasks.** A background recipe runs in a new session of its own (`startRecipe` in `useChatStore`), with an empty history and the task text as its user message. Its system prompt is the session persona's composed prompt with the recipe steps in the `card` segment. The turn does not speak (`speaks` is false), and it cannot start, propose, or judge recipes. It carries the memory tools, with no title counted as stated by the owner.

**Notice turns.** When a background task settles, `notifyConversation` sends its result to the parent conversation as a notice: a user-role message marked with its source. The request renders it with a prefix that says it is not from the owner, and adds one line that lets the model stay quiet. The system prompt is the same composed prompt as a chat turn's. A scene session receives no notice.

**Scene sessions.** A session with a [scene binding](glossary.md#scene-session) answers other people, for example a Discord channel. Its prompt is composed like a chat turn's for the session's character. Its reply returns as text and never speaks on the host, and it gets no recipe or card tools.

**Unprompted turns.** The mind decides when to speak; the model may decline. An unprompted turn starts only from the [character mind](glossary.md#character-mind)'s voice channel: the mind yields a `speak` [intent](glossary.md#intent) for every reach-out, every spoken touch reaction, and every [widget reaction](glossary.md#widget-reaction), and `speak` of `useSituationStore` (`packages/stage-ui/src/stores/situation/index.ts`), the voice port, runs its chat turn: `submitUnprompted` in `useChatStore` for a reach-out and for a widget line (with `widget: true`), and `submitReaction` for a touch line. All go through the same send preparation as a typed turn, with the session's character. The instruction becomes the `unprompted` segment: the reason's instruction for a reach-out, `base.prompt.unprompted-widget` for a widget line, and the touch instruction for a reaction. A reach-out instruction gains one extra sentence while the [character state](glossary.md#character-state) reads as pointed. The payload's `supplement` becomes the `plugin` segment. The trigger message is a user-role history message, not a segment. The turn carries only the read-memory tool (`READ_MEMORY_TOOL_NAME` in `packages/stage-ui/src/tools/memory.ts`). Every unprompted instruction offers the decline marker from `STAGE_RUNTIME_CONFIG`, widget and plugin turns included, and a widget caller always receives the outcome as a `ChatUnpromptedResult`.

**Spark Notify.** A notify takes two separate routes.

- The spoken reaction is an unprompted turn. `ingestSparkNotify` in `packages/stage-ui/src/stores/situation/sensors/notify.ts` folds the notify into the [situation](glossary.md#situation), and the gate decides whether she speaks about it. A plugin that asks for a widget reaction goes through `useContextBridgeStore` in `packages/stage-ui/src/stores/mods/api/context-bridge.ts`, which sends the request to the mind through `requestVoice` and passes the plugin's appended system instructions as `supplement`, so they land in the capped `plugin` segment. `pluginInstructionsText` in `packages/stage-ui/src/stores/chat/prompt.ts` drops blank entries and joins the rest with a blank line, on both routes. Either way, the prompt is the unprompted-turn prompt above, built for the session's character.
- The commands-only agent runs in `useCharacterOrchestratorStore` in `packages/stage-ui/src/stores/character/orchestrator/store.ts`, and only for a notify addressed to a module besides the character or one that forces a Spark command. Its system prompt is `composePrompt(buildChatPromptSegments(...)).text` for the active session's character, through `personaOf` in `useChatSessionStore`. The host instruction (`base.prompt.spark-notify`) is the `spark` segment, and the caller's `appendSystemInstructions`, joined by `pluginInstructionsText`, are the capped `plugin` segment. It has no sticker, voice, control, or unprompted segment. `createSparkNotifyAgent` in `packages/core-agent/src/agents/spark-notify/agent.ts` sends the composed text as the whole system turn and appends nothing; a blank prompt sends no system turn. The live state from `useStageLiveStatePrompt` rides in the user message. The provider and model are the Consciousness module's active selection, and the request sends the output cap for them.

**qa-tools full-prompt fixture.** `buildSystemPrompt` in `packages/qa-tools/src/model/stage-contract.ts` composes the format rules, a card prompt read from a file (or an empty card), an optional register section, and the contract rendered from the installed locale messages. It adds the `actions` segment from `--exposed-actions`, and with `--full` it adds the tail segments that `segmentsFromFixture` in `packages/qa-tools/src/model/prompt.ts` reads from a fixture. `runPromptCli` in the same file is the command-line entry point. qa-tools cannot import stage-ui, so the fixture carries copies of stage-ui's memory header and index lines, and `packages/stage-ui/src/stores/chat/prompt-fixture-parity.test.ts` fails when they drift.

**Outside the composer.** The artistry director in `useAutonomousArtistryStore` in `packages/stage-ui/src/stores/modules/artistry-autonomous.ts` is not a character turn. It writes its own system prompt and appends `composeMemoryPrompt` from `packages/stage-ui/src/tools/memory.ts` with the full index of the card being processed, so its [memory index](glossary.md#long-term-memory) has no entry or char cap.

These requests are not character turns either. Each builds its own prompt without `composePrompt`: expression tag suggestions (`requestExpressionTagSuggestions`), vision inference (`useVisionInference`), the voice end judge (`createVoiceEndJudgeAgent` in `packages/agents/src/voice-end-judge/index.ts`, run by `useVoiceEndJudge`), voice rephrasing (`createVoiceTranscriptionRephraseAgent` in `packages/agents/src/voice-transcription-rephrase/index.ts`, run by `useVoiceRephrase`), tool cards (`createToolCardAgent` in `packages/agents/src/tool-card/index.ts`, run by the leader in `packages/stage-ui/src/stores/tool-cards.ts` with the default chat provider and model), thread extraction (`createThreadExtractor`, run by `useSituationStore` and capped at `EXTRACTION_MAX_TOKENS`), provider validation pings (`createOpenAICompatibleValidators` in `packages/provider-inference`), and the Minecraft bot's `LLMAgent` (`integrations/minecraft`).

## Who may add a segment

- A new system-prompt segment needs a row in `PROMPT_SEGMENT_ORDER` and in `PROMPT_SEGMENT_BUDGETS` in `packages/stage-shared/src/stage-contract/compose.ts`, and an amendment to the [prompt composition ADR](../adr/2026-11-01-prompt-composition.md). The code enforces the first part: `PROMPT_SEGMENT_BUDGETS` must cover every `PromptSegmentId`, the `PromptSegment` type accepts only known ids and the list shape for `drop-oldest` segments, and `composePrompt` throws on an unknown or duplicate id at run time. Nothing in code enforces the ADR amendment.
- In the app, only `buildChatPromptSegments` in `packages/stage-ui/src/stores/chat/prompt.ts` assembles character-turn segments. A path that needs another request-owned part adds a field to `ChatPromptInput`, not its own concatenation. qa-tools mirrors the shapes in `segmentsFromFixture` and must change with them.
- Recipe steps and tool guidance are fields of `ChatPromptInput` (`cardSupplement` and `toolGuidance`), not segments. They share the budget of the segment they ride in. Recipe steps are text that the owner wrote or approved, and they carry system authority.
- Plugins cannot add a segment. Plugin text with system authority reaches a character turn only as the capped `plugin` segment, on both Spark Notify routes: the `supplement` of an unprompted turn, and the caller's `appendSystemInstructions` on the commands-only agent. That segment is part of the system message, and its 2000-char cap is the limit on that authority. Plugin text in the user message, such as `replaceUserMessage` and `appendUserSections`, is not capped.
- `packages/core-agent` holds no stage prompt text. Its Spark Notify agent receives a composed system prompt from the host. The exception is the eval oracle, `packages/core-agent/src/runtime/cue-compliance.ts` and `packages/core-agent/src/runtime/cue-contract-fixtures.ts`, which stays in core-agent because qa-tools scores against it.
- The situation block, the trigger message of an unprompted turn, and per-message timestamps are not segments and must stay out of the system prompt.

## Stored text

The situation block is never stored, but the model can copy a title from it into text that is stored. Code keeps a held title out of that text. `heldTitles` in `packages/stage-shared/src/situation/held-titles.ts` lists the titles the [situation](glossary.md#situation) holds: the foreground window title and the page and video titles of web extension context. `repeatsHeldTitle` in the same file answers whether a text contains one of them whole, ignoring case and whitespace differences. A title shorter than `HELD_TITLE_MIN_CHARS` (8) never matches. While the user shares no titles, the list is empty and nothing is filtered.

- **Memory writes.** `builtIn_writeMemory` checks every entry with `memoryWriteRefusal` in `packages/stage-ui/src/tools/memory.ts` before it saves it. An entry whose description or body repeats a held title is refused, unless the user's own message of the same turn contains that title. An unprompted turn has no user message, and a notice or a background task carries text the owner did not write, so the exception never applies there. An entry that matches a credential shape (a provider key prefix such as `sk-` or `ghp_`, or a `password:` style pair with a value) is always refused. A refused entry is not saved, the tool result tells the model why in one sentence, and the other entries of the call are saved. The sentences in `composeMemoryHeader` stay the main rule; the code covers only these shapes.
- **Trigger messages.** The trigger message of an unprompted turn is stored in chat history with its topic text. The voice port's `speak` in `useSituationStore` passes that text through `unpromptedTopicText` in `packages/stage-shared/src/situation/reducer.ts` for a reach-out and for a widget line. For a topic of the web extension (`WEB_EXTENSION_SOURCE`) the function returns only the kind of topic, so the page or video title and link reach the model through the situation block alone. The headline and note of every other plugin are stored unchanged.
- **Extracted threads and relationship events.** `createThreadExtractor` in `packages/stage-ui/src/features/situation/thread-extraction.ts` drops a thread whose summary or cue repeats a held title, and an event whose reason or memory text does. The other entries of the same answer are kept, and the answer is not recorded as invalid.
- **MOOD cue reasons.** `useCharacterStateStore` in `packages/stage-ui/src/stores/character-state.ts` applies nothing for a MOOD cue whose reason repeats a held title. `parseMoodCue` in `packages/stage-shared/src/character-state/cue.ts` is unchanged.

Dropped threads, events, and cues are dropped silently: the model is told only about a refused memory write.

## Known gaps

Each item states what an ADR says, what the code does, and where. None is fixed here.

- **The memory ADR places `memory` first in the tail.** The 2026-11-01 amendment of the [memory adoption ADR](../adr/2026-10-30-long-term-memory-adoption.md) says that the memory index is the first tail segment. Since the 2026-11-04 amendment of the [prompt composition ADR](../adr/2026-11-01-prompt-composition.md), `actions` leads the tail, and `PROMPT_SEGMENT_ORDER` in `packages/stage-shared/src/stage-contract/compose.ts` follows that order.
- **The situational presence ADR still says that unprompted turns carry no tools.** The [situational presence ADR](../adr/2026-10-19-situational-presence.md) states in its Decision, and again under Alternatives, that an unprompted turn carries no tools. `useChatStore` in `packages/stage-ui/src/stores/chat.ts` gives every unprompted turn the read-memory tool (`READ_MEMORY_TOOL_NAME`) through the runtime's `unpromptedTools` option. The [memory adoption ADR](../adr/2026-10-30-long-term-memory-adoption.md) and the [nonverbal channels ADR](../adr/2026-10-31-nonverbal-channels.md) both state the read tool, so only the presence ADR text is stale.
- **The card segment carries a second expression instruction.** Upstream's card-owned Live2D controls add an ACT section to the `card` segment through `formatLive2DActPrompt`, for the active card only. The fork's stage contract and `actions` segment already tell the model how to cue expressions and clips. A character turn for the active card can therefore carry both, and a session whose character is not the active card gets the contract alone. No ADR covers the overlap; slice CM1 of the [character mind roadmap](character-mind-roadmap.md) reconciles the two expression systems.
- **Recipe steps and tool guidance have no budget of their own.** The [prompt composition ADR](../adr/2026-11-01-prompt-composition.md) gives every part of the system prompt a segment and a budget. Recipe steps ride in `card`, which is flagged but never cut, and card guidance rides in `toolset`.
- **A background task's result is capped like a spoken reply.** The output cap backs the contract's reply-shape rules for speech. A background task turn does not speak, but it goes through the same resolver in `useChatStore` and gets the same cap.
- **Recipe proposals and notices are stored without the held-title check.** The stored-text rules above cover memory writes, trigger messages, extracted threads, relationship events, and MOOD cue reasons. A recipe that the model proposes (`createProposeRecipeTool`) and the result text of a background task, which `notifyConversation` stores in chat history, pass no `repeatsHeldTitle` check.
- **`packages/stage-ui/src/stores/chat/prompt-recipe.ts` keeps an unused second composer.** Upstream's `CHAT_FORMAT_RULES` and its own `composeSystemPrompt` remain in the file beside `composeRecipeSpacePrompt`. Only their test calls them; every app path composes through `composePrompt`.
