# LLM prompt

Verified against the code on 2026-11-16 (commit `1976c952b`). These rules win over the ADRs in `docs/ai/adr/`; the ADRs record the history behind them.

The system prompt of every character turn is built by one pure function, `composePrompt` in `packages/stage-shared/src/stage-contract/compose.ts`. It reads no locale, store, or clock. It sorts the supplied [segments](glossary.md#prompt-segment) by `PROMPT_SEGMENT_ORDER`, fits each segment to its entry in `PROMPT_SEGMENT_BUDGETS`, drops empty segments, and joins the rest with a blank line. The one exception to the join is that the card follows the format rules directly. The function returns the full text, the prefix, the tail, and a size report with one entry per supplied segment. An unknown or duplicate segment id throws. Overflow never throws.

Hosts render the segment texts. In the app, `useChatPrompt` in `packages/stage-ui/src/stores/chat/prompt.ts` returns `buildChatPromptSegments`, which is the only builder of character-turn segments. Every app path that makes the character speak calls it. See [Paths](#paths).

## Segments

The overflow policies are defined by `OverflowPolicy` in `packages/stage-shared/src/stage-contract/compose.ts`:

- `fixed`: host-written text with no budget. It is never cut or flagged.
- `warn`: the text is kept, and the report sets `overBudget`. Nothing is cut.
- `truncate`: text over the budget is cut, and `PROMPT_TRUNCATION_MARKER` is appended inside the budget.
- `drop-oldest`: list entries are dropped from the front until the entry cap and the char cap both hold. The header is not counted, and it stays when every entry is dropped.

The "enforced in code?" column states what `composePrompt` does when a segment is over its budget. Budgets are in characters, not tokens.

The prefix (`format`, `card`, `register`, `contract`) changes only when the card, the [conversation register](glossary.md#conversation-register), or the locale of the contract changes. The provider's prompt cache depends on it. The tail follows the prefix, and `actions` leads the tail because the exposed clips change only when the user curates them. `composeSystemPrompt` in `packages/stage-shared/src/stage-contract/index.ts` returns the prefix of the format, card, and contract segments. With a register section joined to the card, its output is byte-identical to the composed prefix.

These parts of a request are not system-prompt segments and do not pass through the composer: the [situation block](glossary.md#situation-block) and the [character context](glossary.md#character-context), which the runtime attaches to the last user turn through the runtime context providers of `useChatStore` in `packages/stage-ui/src/stores/chat.ts`; the trigger message of an [unprompted turn](glossary.md#reach-out); per-message timestamps; and tool schemas.

The output cap is not a segment. `REPLY_MAX_TOKENS` (320) in `packages/stage-shared/src/stage-contract/index.ts` is sent as `maxTokens` on every model request of chat turns, `ingest`, unprompted turns, and the [Spark Notify](glossary.md#spark-notify) agent.

## Paths

**Chat turns (typed and voice).** `useChatStore` in `packages/stage-ui/src/stores/chat.ts` prepares a send and builds a resolver that runs before each model request, so a tool step that edits the card or memory reaches the next request. The resolver reads the character that owns the session, not the selected card. It calls `buildChatPromptSegments` with that character, the voice context and control events of a voice turn, and the sticker catalog from the stickers store. It then composes the prompt with `composePrompt` and sends `REPLY_MAX_TOKENS`. The provider and model come from that character's card. The runtime, `createChatOrchestratorRuntime` in `packages/core-agent/src/runtime/chat-orchestrator-runtime.ts`, sends the composed text as the system message and also writes the first request's prompt into the display projection, so hooks and diagnostics see what was sent. The stored session system message, which `useChatSessionStore` in `packages/stage-ui/src/stores/chat/session-store.ts` builds with `composeSystemPrompt` from the card, the register section, and the contract, is replaced for every request that has a resolver. Every chat path in `useChatStore` passes a resolver.

**`ingest`.** The `ingest` action of `useChatStore` sends a message with the caller's provider, model, temperature, and top-p. It captures `buildChatPromptSegments` once, when it is called, for the session's character, and adds the sticker segment from the caller's catalog or the stickers store. It never supplies `voice`, `control`, `unprompted`, or `plugin`. It sends the same `REPLY_MAX_TOKENS` cap through the same resolver as chat turns, and it adds no memory tools of its own. The callers in this branch are devtools and stress tools, for example `useMarkdownStressStore` in `packages/stage-ui/src/stores/markdown-stress.ts`.

**Unprompted turns.** `useChatStore` starts an unprompted turn with `submitUnprompted` ([gate](glossary.md#gate) reach-outs and forced turns) or `submitReaction` (spoken [touch reactions](glossary.md#touch-reaction)). Both go through the same send preparation as a typed turn, with the session's character. The instruction becomes the `unprompted` segment. A reach-out instruction gains one extra sentence while the [character state](glossary.md#character-state) reads as pointed. The payload's `supplement` becomes the `plugin` segment. The trigger message is a user-role history message, not a segment. The turn carries only the read-memory tool (`READ_MEMORY_TOOL_NAME` in `packages/stage-ui/src/tools/memory.ts`), and the model can decline it with the decline marker from `STAGE_RUNTIME_CONFIG`.

**Spark Notify.** A notify takes two separate routes.

- The spoken reaction is an unprompted turn. `ingestSparkNotify` in `packages/stage-ui/src/stores/situation/sensors/notify.ts` folds the notify into the [situation](glossary.md#situation), and the gate decides whether she speaks about it. A plugin that asks for a widget reaction goes through `useContextBridgeStore` in `packages/stage-ui/src/stores/mods/api/context-bridge.ts`. That store calls `submitUnprompted` with `force: true` and passes the plugin's appended system instructions as `supplement`, so they land in the capped `plugin` segment. Either way, the prompt is the unprompted-turn prompt above, built for the session's character.
- The commands-only agent runs in `useCharacterOrchestratorStore` in `packages/stage-ui/src/stores/character/orchestrator/store.ts`, and only for a notify addressed to a module besides the character or one that forces a Spark command. Its system prompt is `composePrompt(buildChatPromptSegments(...)).text` for the active card, not the session's character. It has no sticker, voice, control, unprompted, or plugin segment. `createSparkNotifyAgent` in `packages/core-agent/src/agents/spark-notify/agent.ts` appends after the composed text, outside the composer and its report: the host instruction (`base.prompt.spark-notify`), the caller's `appendSystemInstructions`, and any plugin system instructions. The live state from `useStageLiveStatePrompt` rides in the user message. The provider and model are the Consciousness module's active selection, and the request sends `REPLY_MAX_TOKENS`.

**qa-tools full-prompt fixture.** `buildSystemPrompt` in `packages/qa-tools/src/model/stage-contract.ts` composes the format rules, a card prompt read from a file (or an empty card), an optional register section, and the contract rendered from the installed locale messages. It adds the `actions` segment from `--exposed-actions`, and with `--full` it adds the tail segments that `segmentsFromFixture` in `packages/qa-tools/src/model/prompt.ts` reads from a fixture. `runPromptCli` in the same file is the command-line entry point. qa-tools cannot import stage-ui, so the fixture carries copies of stage-ui's memory header and index lines, and `packages/stage-ui/src/stores/chat/prompt-fixture-parity.test.ts` fails when they drift. The fixture schema accepts an `account` segment, which no app path emits.

**Outside the composer.** The artistry director in `useAutonomousArtistryStore` in `packages/stage-ui/src/stores/modules/artistry-autonomous.ts` is not a character turn. It writes its own system prompt and appends `composeMemoryPrompt` from `packages/stage-ui/src/tools/memory.ts` with the full index of the card being processed, so its [memory index](glossary.md#long-term-memory) has no entry or char cap.

## Who may add a segment

- A new system-prompt segment needs a row in `PROMPT_SEGMENT_ORDER` and in `PROMPT_SEGMENT_BUDGETS` in `packages/stage-shared/src/stage-contract/compose.ts`, and an amendment to the [prompt composition ADR](../adr/2026-11-01-prompt-composition.md). The code enforces the first part: `PROMPT_SEGMENT_BUDGETS` must cover every `PromptSegmentId`, the `PromptSegment` type accepts only known ids and the list shape for `drop-oldest` segments, and `composePrompt` throws on an unknown or duplicate id at run time. Nothing in code enforces the ADR amendment.
- In the app, only `buildChatPromptSegments` in `packages/stage-ui/src/stores/chat/prompt.ts` assembles character-turn segments. A path that needs another request-owned part adds a field to `ChatPromptInput`, not its own concatenation. qa-tools mirrors the shapes in `segmentsFromFixture` and must change with them.
- Plugins cannot add a segment. Their text reaches a character turn only as the capped `plugin` segment, which they supply through the `supplement` of an unprompted turn.
- `packages/core-agent` holds no stage prompt text. Its Spark Notify agent receives the host instruction as a function. The exception is the eval oracle, `packages/core-agent/src/runtime/cue-compliance.ts` and `packages/core-agent/src/runtime/cue-contract-fixtures.ts`, which stays in core-agent because qa-tools scores against it.
- The situation block, the trigger message of an unprompted turn, and per-message timestamps are not segments and must stay out of the system prompt.

## Known gaps

Each item states what an ADR says, what the code does, and where. None is fixed here.

- **The `account` segment has no producer.** The [prompt composition ADR](../adr/2026-11-01-prompt-composition.md) lists `account` as segment 8 (`warn`, 2000 chars), and its 2026-11-01 amendment says that Spark receives "the toolset and account text". No app path supplies an `account` segment: `buildChatPromptSegments` in `packages/stage-ui/src/stores/chat/prompt.ts` never emits it. Only the qa-tools fixture schema in `segmentsFromFixture` (`packages/qa-tools/src/model/prompt.ts`) accepts it.
- **Plugin text on the Spark Notify agent is not capped.** The [prompt composition ADR](../adr/2026-11-01-prompt-composition.md) owner decisions say that plugin text keeps system authority with a 2000-char cap, and that over-cap text is truncated and flagged. On the commands-only agent, `createSparkNotifyAgent` in `packages/core-agent/src/agents/spark-notify/agent.ts` appends the caller's `appendSystemInstructions` and plugin system instructions after the composed prompt, with no cap and no report entry. `useCharacterOrchestratorStore` in `packages/stage-ui/src/stores/character/orchestrator/store.ts` passes the caller's control through to it. The spoken route caps the same text, because `useContextBridgeStore` passes it as the `plugin` segment.
- **Spark Notify does not receive the same segments as chat.** The 2026-11-01 amendment of the [prompt composition ADR](../adr/2026-11-01-prompt-composition.md) says that Spark receives the same segments as chat. The commands-only agent in `useCharacterOrchestratorStore` builds segments for the active card without stickers, voice, control, unprompted, or plugin, so it receives the prefix plus `actions`, `memory`, and `toolset`.
- **Spoken Spark Notify reactions use the session character's memory, not the active card's.** The [memory adoption ADR](../adr/2026-10-30-long-term-memory-adoption.md) says that "the Spark Notify prompt uses the active card's index", and the [prompt composition ADR](../adr/2026-11-01-prompt-composition.md) owner decisions say that Spark Notify reactions use the active card's memory. Spoken reactions are now unprompted turns, started by the gate or by `useContextBridgeStore` through `submitUnprompted` in `useChatStore` (`packages/stage-ui/src/stores/chat.ts`), and they read the memory of the character that owns the active session. Only the commands-only agent in `useCharacterOrchestratorStore` reads the active card. The two characters differ only when the active session belongs to another card.
- **The memory ADR places `memory` first in the tail.** The 2026-11-01 amendment of the [memory adoption ADR](../adr/2026-10-30-long-term-memory-adoption.md) says that the memory index is the first tail segment. Since the 2026-11-04 amendment of the [prompt composition ADR](../adr/2026-11-01-prompt-composition.md), `actions` leads the tail, and `PROMPT_SEGMENT_ORDER` in `packages/stage-shared/src/stage-contract/compose.ts` follows that order.
- **The situational presence ADR still says that unprompted turns carry no tools.** The [situational presence ADR](../adr/2026-10-19-situational-presence.md) states in its Decision, and again under Alternatives, that an unprompted turn carries no tools. `useChatStore` in `packages/stage-ui/src/stores/chat.ts` gives every unprompted turn the read-memory tool (`READ_MEMORY_TOOL_NAME`) through the runtime's `unpromptedTools` option. The [memory adoption ADR](../adr/2026-10-30-long-term-memory-adoption.md) and the [nonverbal channels ADR](../adr/2026-10-31-nonverbal-channels.md) both state the read tool, so only the presence ADR text is stale.
